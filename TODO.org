* Design principle: open-ended client (octocrab-style escape hatch)
:PROPERTIES:
:CATEGORY: design
:END:

The Salesforce REST surface is large and growing. We will *not* race
Salesforce to wrap every endpoint. Instead, the client must always
expose a low-level escape hatch so a user can call any
=/services/data/...= URL we haven't typed yet — without giving up auth,
the configured instance URL, retry policy, or =tracing= spans.

This is the same contract [[https://github.com/XAMPPRocky/octocrab][Octocrab]] offers for GitHub: typed
builders for the common surface, plus =get= / =post= / =put= / =patch=
/ =delete= methods that take a path + serializable body and return
either typed JSON or =serde_json::Value=.

** Required surface
- =Client::get<R: DeserializeOwned>(path, query) -> Result<R>=
- =Client::post<B: Serialize, R: DeserializeOwned>(path, body) -> Result<R>=
- =Client::put / patch / delete= — symmetrical
- =Client::execute(reqwest::Request) -> Result<reqwest::Response>= —
  full bypass for unusual cases (multipart upload, custom headers,
  binary download, SSE).
- =Client::request_builder(method, path) -> reqwest::RequestBuilder=
  — pre-authenticated, pre-baseurl'd, but not yet sent. Lets the
  caller compose anything reqwest can express.

** Path semantics
- Relative path (=sobjects/Account/001...=) → resolved against
  =instance_url + /services/data/{version}/=.
- Path with leading =/= (=/services/apexrest/foo=) → resolved against
  =instance_url= directly. Mirrors how Salesforce's own
  =nextRecordsUrl= comes back as an absolute path under the instance.
- Fully-qualified =https://...= URL → used as-is. Useful for
  =nextPageUrl= / Bulk 2.0 job result locators.

** What still flows through automatically
- =Authorization: Bearer ...= header from the configured =AuthFlow=
  (refresh-on-401 still applies).
- Configured =api_version= for relative paths.
- Retry / backoff (once that lands).
- =tracing= span around the request (once that lands).

** Why this matters now (not later)
- Unblocks every "we don't have a builder for X yet" complaint with a
  one-liner answer.
- Forces us to design the =Client= around composable layers
  (auth → base URL → request) instead of letting typed builders
  accidentally short-circuit those layers.
- Lets us *delete* speculative typed builders if usage data shows the
  raw escape hatch is fine; we can't easily un-ship a typed wrapper.

** Non-goals
- We do *not* try to make the escape hatch ergonomic enough to replace
  builders for high-traffic resources. CRUD, query, search etc. should
  feel nicer than the raw call.
- We do *not* expose internal modules (=token_endpoint=, etc.) just
  because the escape hatch exists. The escape hatch is for *Salesforce
  REST*, not for our auth internals.

* Phase 1 — MVP REST API surface [7/10]
:PROPERTIES:
:GOAL: Exercise the auth layer end-to-end and lock in the request/response/handler shape that all later tiers reuse.
:END:
** DONE =/services/data= — list versions (=handlers::versions=)
** DONE =/services/data/vXX.X/limits= (=handlers::limits=)
- Typed =Limit= envelope handles the =PermissionSets.CreateCustom= nested case via =#[serde(flatten)]=.
** DONE =/services/data/vXX.X/sobjects/= — describe global (=handlers::sobjects::SObjectsHandler=)
- Typed =DescribeGlobal= + =SObjectMetadata=. =urls= map kept generic to absorb new keys across API versions.
** DONE =/services/data/vXX.X/sobjects/{SObject}/describe= (=SObjectHandler::describe=)
- Returns =serde_json::Value= by default; =describe_as::<T>()= for typed callers.
** DONE SObject CRUD [5/5]
- [X] =GET    /sobjects/{SObject}/{id}= — =retrieve= / =retrieve_with_fields=, plus =_as::<T>= variants
- [X] =POST   /sobjects/{SObject}= — =create=
- [X] =PATCH  /sobjects/{SObject}/{id}= — =update=
- [X] =DELETE /sobjects/{SObject}/{id}= — =delete=
- [X] =PATCH  /sobjects/{SObject}/{ExternalIdField}/{value}= — =upsert= (external value is percent-encoded via =Url::path_segments_mut=)
** DONE =/services/data/vXX.X/query= + =/queryAll= (=handlers::query=)
- =query=, =query_all=, =query_more= on =Cloudburst=, each with =_as::<T>()= typed variants returning =QueryResult<R>=.
- =query_more= goes through =get_unversioned= because the =nextRecordsUrl= locator is instance-relative and carries the *originating* API version (locator wins over client config — Salesforce-mandated).
- Pagination iterator/stream wrapper still pending — tracked under cross-cutting infrastructure.
** DONE =/services/data/vXX.X/search= and =/parameterizedSearch= (=handlers::search=)
- =search(sosl)= for SOSL strings; =parameterized_search(body)= for the structured POST form.
- =SearchResult<R>= envelope alongside =QueryResult<R>=; =metadata= surfaced as raw =serde_json::Value= because its shape changes across versions.
- *Deliberately omitted:* the =GET /parameterizedSearch?q=…&sobject=…= form. The POST form is strictly more capable; if a caller really needs the GET form they can hit it via the open-ended client escape hatch (once it lands).
** DONE =/services/data/vXX.X/composite/batch= (=handlers::composite=)
- =Cloudburst::composite().batch(body)= sends up to 25 sub-requests in one round trip and returns =BatchResponse= with =has_errors= + =Vec<BatchSubresult>=.
- Typed =BatchRequest= / =BatchSubrequest= request structs in =handlers::composite=, alongside =serde_json::json!({...})= bodies via the generic =Serialize= bound.
- Per-subrequest failures are *not* translated into transport errors — Salesforce returns HTTP 200 for the outer call and the caller inspects =has_errors= + =BatchSubresult::is_success()=. Top-level batch deserialization errors (e.g. invalid sub-request URL) still surface as =CloudburstError::Api=.
- Sub-request URLs do not flow through =resolve_url=; they are version-prefixed strings (=v60.0/sobjects/...=) per Salesforce's documented dispatch under =/services/data/=.

* Phase 2 — Power-user surface [2/?]
:PROPERTIES:
:GOAL: Cover the requests jsforce/simple-salesforce users reach for after CRUD.
:END:
** DONE Composite tree =/composite/tree/{SObject}= (=handlers::composite::tree=)
- =Cloudburst::composite().tree(sobject, body)= POSTs an arbitrary tree envelope and returns =CompositeTreeResponse= with =has_errors= + =Vec<CompositeTreeResult>=.
- Distinct =CompositeError= struct (renamed from =CompositeTreeError= when shared with =/composite/sobjects=) because Salesforce uses =statusCode= (string enum, e.g. =INVALID_EMAIL_ADDRESS=) here instead of the standard =errorCode= surfaced by =SalesforceError=.
- *All-or-nothing semantics:* if =has_errors= is true, the entire tree was rolled back — =results= lists only the failing =referenceId=s, not all records. Documented on the response struct so callers don't iterate looking for partial successes.
- Limits documented in handler: 200 records total, 5 distinct sObject types, 5 levels of nesting.
** DONE Composite collections =/composite/sobjects= (=handlers::composite::sobjects=)
- =Cloudburst::composite().sobjects()= sub-handler with =create=, =update=, =upsert=, =delete=, =retrieve= / =retrieve_as=. All return =Vec<SObjectCollectionResult>= except retrieve which returns =Vec<Value>= / =Vec<R>=.
- Default semantics are *partial-success* (=allOrNone: false=) — distinct from =/composite/tree=. Caller sets =allOrNone: true= in the body / query string for transactional behavior.
- Per-record errors share =CompositeError= with =/composite/tree= (same diverged =statusCode= shape).
- =retrieve= surfaces missing records as =Value::Null= entries aligned 1:1 with input =ids=. Typed =retrieve_as::<Option<R>>()= is the documented idiom for handling them.
- =upsert= surfaces newly-inserted vs updated records via =SObjectCollectionResult::created= (=Some(true)= / =Some(false)=); always =None= for non-upsert calls.
- *TODO consolidation:* the previously-listed "SObject collections — record-set CRUD wrappers" is *not* a separate endpoint. It's now a potential ergonomic-sugar layer over =composite().sobjects()= (e.g. =sf.sobjects().create_many(records)=) — deferred until usage data shows it's worth the parallel surface.

** TODO Property tests for URL / encoding / parser invariants [#B]
- *What:* Add =proptest= as a dev-dependency and write property tests for the cheap-but-load-bearing helpers:
  - =Cloudburst::versioned_segments= — for any segment string, the resulting URL parses back to the same segments and never contains =//= outside the scheme.
  - =Cloudburst::versioned_url= / =Cloudburst::instance_url= — round-trip stability with arbitrary leading/trailing slashes on the path.
  - =response::parse_response_bytes= — for any =(status, bytes)= input, the function returns =Result= and never panics. Pairs naturally with =unwrap_used = "deny"= already in =Cargo.toml=.
  - SOQL escaping (when we add a builder) — escaped strings parse back to the original.
- *Why:* The trailing-slash bug we hit during sObject CRUD would have been caught by a one-line property invariant. Property tests are the cheapest way to lock invariants on this layer.
- *Effort:* Small. ~1 day to add =proptest=, write ~5 properties, integrate with =cargo nextest=.

** TODO Live integration tests against a Salesforce dev/scratch org [#A]
- *What:* End-to-end tests that hit a real Salesforce org over HTTPS, gated behind an environment variable so they never run in default CI.
  - Suggested gate: =CLOUDBURST_INTEGRATION=1= + =CLOUDBURST_INTEGRATION_INSTANCE_URL= + a token (from a sops-encrypted file or =.env=).
  - Place under =tests/integration/= as a separate test target with =#[ignore]= on every test, opted in via =cargo nextest run --run-ignored only=.
  - Starter suite: auth round-trip (JWT bearer), =versions=, =limits=, one sObject CRUD cycle on a disposable record (create → retrieve → update → delete), one =query= round-trip with pagination.
  - Hard guard: refuse to run if =CLOUDBURST_INTEGRATION_INSTANCE_URL= contains =my.salesforce.com= (production My Domain) without an explicit =CLOUDBURST_INTEGRATION_ALLOW_PRODUCTION=1= override.
- *Why:* Mock tests assert against the wire shape *we wrote*. Only real responses falsify our assumptions about Salesforce — wire-shape drift across releases is the highest-impact bug class for an HTTP SDK and nothing else catches it.
- *Effort:* Medium. Half-day for the harness + guards, ~1 day to flesh out the starter suite. CI integration optional (can stay developer-run until 1.0).
- *Dependency:* Needs a Salesforce dev/scratch org. SFDX can spin scratch orgs on demand if we want truly disposable per-run orgs, but a long-lived dev org is fine for v1.
